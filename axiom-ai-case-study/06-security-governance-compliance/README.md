# Security Governance & Compliance

## Overview

This project represents the final stage of the **Axiom AI Technologies** cybersecurity case study.

The objective is to demonstrate how an organization can establish, operate, monitor, and continually improve an information security governance and compliance program.

The project builds upon the risk management, controls assessment, ISMS implementation, business continuity, vulnerability management, security remediation, and malware-analysis activities completed in Projects 1–5.

Rather than treating governance and compliance as standalone activities, this project demonstrates how security governance connects the organization's risks, controls, policies, operational activities, management decisions, and continual-improvement processes.

> **Portfolio Disclaimer:** This case study is inspired by and based on real professional cybersecurity and GRC activities. Axiom AI Technologies is a fictional organization, and all findings, assessments, metrics, decisions, and evidence are simulated for portfolio and educational purposes.

# Governance Model

The governance model follows a three-level structure.

```text
Executive Management
        │
        ▼
Security Governance / ISMS Oversight
        │
        ▼
Security & Operational Teams
```

## Executive Management

Responsible for:

* Strategic direction
* Risk acceptance
* Resource allocation
* Security objectives
* Major security decisions
* Review of ISMS performance

## Security Governance / ISMS Oversight

Responsible for:

* ISMS coordination
* Risk management
* Policy governance
* Compliance monitoring
* Control oversight
* Security reporting
* Audit coordination
* Continual improvement

## Operational Teams

Responsible for:

* Implementing security controls
* Monitoring systems
* Responding to incidents
* Managing vulnerabilities
* Maintaining evidence
* Reporting security issues
* Supporting compliance activities

# Governance Principles

Axiom AI's governance model is based on the following principles:

### Accountability

Security responsibilities must be clearly assigned to appropriate individuals or functions.

### Risk-Based Decision Making

Security decisions should be based on documented risk rather than assumptions.

### Evidence-Based Governance

Security claims should be supported by appropriate evidence.

### Management Oversight

Significant information-security risks and performance issues should be visible to management.

### Continual Improvement

The ISMS should evolve based on risks, incidents, audits, performance information, and lessons learned.

### Proportionality

Security controls and governance requirements should be appropriate to the organization's risk profile and business objectives.

# Security Metrics

The governance program incorporates both KPIs and KRIs.

## Example KPIs

* Percentage of security controls assessed
* Percentage of corrective actions completed
* Vulnerability remediation SLA compliance
* Security-training completion rate
* BCP exercise completion
* Security review completion rate
* Percentage of policies reviewed on schedule

## Example KRIs

* Number of overdue High/Critical vulnerabilities
* Number of overdue risk-treatment actions
* Number of unresolved High-risk findings
* Number of security incidents
* Number of repeat security findings
* Number of critical third-party security issues
* Number of failed or overdue recovery tests

Metrics should be reviewed in context rather than interpreted as isolated numbers.

# Compliance Governance

Compliance activities should follow a continuous lifecycle:

```text
Identify Requirements
        ↓
Map Requirements to Controls
        ↓
Collect Evidence
        ↓
Assess Effectiveness
        ↓
Identify Gaps
        ↓
Assign Corrective Actions
        ↓
Validate Remediation
        ↓
Report to Management
        ↓
Continually Monitor
```

This approach prevents compliance from becoming a point-in-time activity performed only immediately before an audit.

---

# Risk Acceptance and Exceptions

The governance framework establishes a controlled approach for security exceptions and risk acceptance.

Exceptions should document:

* Business justification
* Affected asset or process
* Associated risk
* Compensating controls
* Risk owner
* Approval authority
* Expiration date
* Review requirements

Security exceptions should not become permanent alternatives to appropriate control implementation without documented management approval and periodic review.

---

# Document Governance

Security documentation should have:

* Document owner
* Classification
* Version
* Approval authority
* Effective date
* Review frequency
* Revision history
* Status

Documents should be reviewed when:

* Significant organizational changes occur.
* Relevant risks change.
* Security incidents identify weaknesses.
* Applicable requirements change.
* Audit findings require updates.
* Control changes affect documented procedures.
